# Modernize Scripting Subsystem with .NET 10 CoreCLR via Hostfxr

The engine originally used an embedded Mono runtime for C# scripting. However, Mono required external SDK installations, lacked modern C# language features and runtime optimizations, and suffered from brittle assembly search path resolution. An initial refactor toward .NET 10 CoreCLR introduced unnecessary architectural indirection—wrapping two trivial members in a heap-allocated `UniquePtr<Impl>` (PIMPL), duplicating engine fatal macros via a custom `ORC_SCRIPTING_FATAL_CHECK`, scattering `#if defined(ORC_PLATFORM_WINDOWS)` branches across standalone helper functions, and wrapping one-off C-API calls in generic template helpers.

We decided to replace the legacy Mono runtime with a direct, streamlined .NET 10 CoreCLR hosting architecture via Microsoft's `hostfxr` APIs:
- **Canonical Fail-Fast Crash Contract**: `ORC_FATAL` and `ORC_FATAL_CHECK` in `Orc/Engine/Debug.hpp` unconditionally terminate the process via `std::abort()` in both Debug and Release configurations. Every step in the hosting sequence—locating `hostfxr`, loading the dynamic library, resolving hosting exports, loading the runtime configuration, acquiring runtime delegates, and binding managed entry points—uses `ORC_FATAL_CHECK` directly without early-return boilerplate or custom subsystem macros.
- **Direct Class Layout without PIMPL**: `Orc/Script/Scripting.hpp` stores `FilePath m_configPath` and `void* m_hostfxrLib = nullptr` directly on `Scripting` alongside private `loadHostFxr()` and `initializeRuntime()` methods, avoiding heap allocation and pointer-chasing while still keeping public headers completely free of OS headers (`Windows.h`, `dlfcn.h`) and .NET hosting headers (`nethost.h`, `hostfxr.h`, `coreclr_delegates.h`). Resolved `hostfxr` and CoreCLR function pointers (`m_hostfxrInitializeForRuntimeConfig`, `m_hostfxrGetRuntimeDelegate`, `m_hostfxrClose`, `m_loadAssemblyAndGetFunctionPointer`) are encapsulated as private instance member variables of `Scripting`.
- **Deleted Copy and Move Semantics**: Both copy and move operations on `Scripting` are explicitly deleted (`= delete`), preventing duplicate raw library handles or double-freeing without out-of-line move boilerplate. File path parameters use the engine's canonical `const FilePath&` alias.
- **Localized Platform Macros & Direct C-API Calls**: `Scripting.cpp` consolidates platform-specific dynamic library loading and string literal differences into a single top-of-file macro block (`ORC_LOAD_LIB`, `ORC_GET_EXPORT`, `ORC_FREE_LIB`, `ORC_DOTNET_STR`), invoking `hostfxr` and CoreCLR C-APIs directly without template wrappers.
- **`[UnmanagedCallersOnly]` Interop**: Managed C# functions are marked with `[UnmanagedCallersOnly]` and resolved via `loadAssemblyAndGetFunctionPointer` using `UNMANAGEDCALLERSONLY_METHOD`, providing zero-overhead direct function pointer invocation.
- **Nomenclature Synchronization**: Stale Mono identifiers in `Engine` (`m_mono`) were renamed to canonical `Scripting` (`m_scripting`), aligning code and documentation with ubiquitous language.
